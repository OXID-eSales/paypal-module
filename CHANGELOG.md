## [2.9.2] - Unreleased

### FIX

- [0007972](https://bugs.oxid-esales.com/view.php?id=7972): Fix Pay-upon-Invoice (Rechnungskauf) orders permanently losing their PayPal payment / bank details (IBAN, BIC, bank name, payment reference) when the `PAYMENT.CAPTURE.COMPLETED` webhook arrived while the order was still being finalized. Root cause is a transaction-commit-visibility race: `Model/Order::finalizeOrder()` wraps `parent::finalizeOrder()` — which for PUI runs `Service/Payment::doExecutePuiPayment()`, i.e. creates the PayPal order+capture **and** writes the `oscpaypal_order` ↔ `oxorder` mapping via `trackPayPalOrder()` — inside a single DB transaction (the stock-lock transaction) that only commits after `parent::finalizeOrder()` returns. PayPal fires the PUI capture webhook the moment the capture is created (step inside that still-open transaction), so it arrives on a separate connection where the mapping row is not yet committed and therefore invisible; `OrderRepository::getShopOrderByPayPalOrderId()` finds nothing and `WebhookHandlerBase::getOrderByPayPalOrderId()` raises `WebhookEventRetryException`. The module then swallowed that to an HTTP 200 (`WebhookController::init()` always responds 200), and because PayPal only retries on a non-2xx status (up to 25 times over 3 days, per PayPal's webhook docs), the event was marked delivered and **never resent** — so `WebhookHandlerBase::updateStatus()` never ran and the PUI bank data was never persisted (and the buyer's invoice mail lacked the transfer details). Fix: a not-yet-visible order now raises a *retryable* `WebhookEventRetryException` (carrying a `Retry-After`) which `WebhookController` maps to **HTTP 503 + Retry-After** so PayPal redelivers — by the retry the finalize transaction has committed and the lookup succeeds. `WebhookHandlerBase::resolveNotFoundRetryAfter()` decides retry vs give-up via a fixed cap (`ORDER_NOT_FOUND_RETRY_MAX_AGE_SECONDS = 300`) measured against the event's `create_time`: PayPal resends the same event with an unchanged `create_time`, so `now - create_time` grows monotonically across deliveries and the cap is deterministic per event — beyond it (or when `create_time` is absent) the exception is non-retryable and the controller responds 200, exactly as an abandoned express checkout is handled today (no 25x/3-day retry spam; see the log-reclassification entry below). As part of this the webhook HTTP response was moved off the previous raw `exit()` calls onto this exception mapping: `handleWebhookDelay()` now throws the same retryable exception instead of `exit()`-ing a 503, `RequestHandler` rethrows retryable exceptions (and still swallows the benign give-up case to 200), and `WebhookController` performs the single 503-or-200 decision — which also makes the retry behaviour unit-testable (a raw `exit()` cannot be asserted and aborts the test runner). Additionally `isMinimumWaitTimeElapsed()` now treats a missing resource `create_time` as "proceed" instead of "too fresh"; the old default, combined with the retry, would have looped 503 for terminal events whose resource carries no `create_time` (e.g. `CHECKOUT.PAYMENT-APPROVAL.REVERSED`). Files touched: `src/Core/Webhook/Handler/WebhookHandlerBase.php`, `src/Core/Webhook/RequestHandler.php`, `src/Controller/WebhookController.php`, `src/Exception/WebhookEventRetryException.php`.
- [0007970](https://bugs.oxid-esales.com/view.php?id=7970): Consolidate PayPal purchase-unit / patch item building onto a single source, so the amount patch and the items patch can no longer describe different baskets, and reconstruct the full basket for the patch in both net and gross calculation mode. Background: since the PP-Express order rework (`835a94d9`) the order-creation amount and items are built by `Service/Factory/PayPalPurchaseUnitsFactory`, whereas `Core/PatchRequestFactory::getPurchaseUnitsPatch()` still assembled its own, independent, tax-less item list and short-circuited entirely in net calculation mode (`$withItems = !$this->basket->isCalculationModeNetto()` → `return null`). Because `getOrderPatches()` sends the amount patch (from the factory) and the items patch together in one PATCH request, the two halves could describe different item sets: in gross mode the hand-built items (products + gift wrapping + greeting card + payment + surcharge, all tax-less) did not match the factory-derived `breakdown.item_total` (products only), and in net mode no item breakdown was sent at all. Changes: **(1)** `getPurchaseUnitsPatch()` now takes its items from the same `PayPalPurchaseUnitsFactory` instance that `getAmountPatch()` already uses, so amount and items are always computed by one authority and stay consistent — and a net-mode/B2B basket now also receives a proper item breakdown. The net-mode guard, the manual item assembly, the now-unused `getItemCategoryByBasketContent()` helper and the imports only it needed (`Item`, `BasketItem`, `Truncate`, `PriceToMoney`) were removed. **(2)** `PayPalPurchaseUnitsFactory::mapItems()` now emits gift wrapping and greeting card as explicit, correctly taxed line items (net mode: net value + per-unit VAT; gross mode: gross value, no separate tax) next to the existing payment-surcharge item, via a new private `mapCostAsItem()` helper; the payment item now uses the shop's `PAYMENT_METHOD` translation instead of a hard-coded `"Payment surcharge"` label. Because the full basket is now itemised, the `PayPalAmountValidator`'s balancing "Rounding Adjustment" item shrinks back to true cent rounding instead of absorbing the wrapping/gift-card amounts — the validator's balancing rules themselves are unchanged. Shipping stays a breakdown component and discounts keep flowing through the breakdown discount as before. Also removed the orphaned `$withItems` variable in `Service/Factory/OrderRequestFactory::getRequest()` that `835a94d9` left behind (it stopped being consumed when purchase-unit building moved to the factory). Files touched: `src/Core/PatchRequestFactory.php`, `src/Service/Factory/PayPalPurchaseUnitsFactory.php`, `src/Service/Factory/OrderRequestFactory.php`.
- Remove a redundant `$isVaulting` / `ModuleSettings` lookup at the top of `Service/Factory/OrderRequestFactory::getRequest()` that was overwritten before its first use (the same value is fetched again a few lines further down). No behaviour change. Files touched: `src/Service/Factory/OrderRequestFactory.php`.
- Remove dead, duplicated purchase-unit building from `Service/Factory/OrderRequestFactory` that `835a94d9` left behind when it moved that logic to `Service/Factory/PayPalPurchaseUnitsFactory` (`getRequest()` has since called `$this->purchaseUnitsFactory->getPurchaseUnits(...)`). The five methods reachable only from the no-longer-called local `getPurchaseUnits()` — `getPurchaseUnits()`, `getAmount()`, `getItems()`, `getItemCategoryByBasketContent()` and `getShippingAddress()` — and the imports used solely by them were removed. The live request building and the purchase-unit building in `PayPalPurchaseUnitsFactory` are unaffected; `getBillingAddress()`/`getPayer()`/`getPayerPhone()` stay because they are still used by the live payer path. Note: `getAmount()`, `getItems()` and `getItemCategoryByBasketContent()` were `public`, so this is technically an API removal — but they were unreachable dead duplicates. Files touched: `src/Service/Factory/OrderRequestFactory.php`.
- [0007971](https://bugs.oxid-esales.com/view.php?id=7971): Honor the shop's B2B net/gross *view mode* when building PayPal amounts and the express-button visibility, so a B2B module that overrides `User::isPriceViewModeNetto()` actually takes effect on the PayPal side. The module previously read the raw shop setting `Registry::getConfig()->getConfigParam('blShowNetPrice')` directly, bypassing OXID's user-aware resolution chain (`Basket::isPriceViewModeNetto()` delegates to `User::isPriceViewModeNetto()` whenever a basket user exists, and only falls back to `blShowNetPrice` otherwise). As a result, in a B2B setup where the net/gross mode is decided per customer / customer-group via a `User` override, the PayPal line items and totals were computed from the shop default while the customer was shown and charged the other mode — producing an amount mismatch toward PayPal. Fix: resolve the view mode through the user-aware `isPriceViewModeNetto()` wherever the basket is available — `Model/Basket::getPayPalCheckoutItems()` now calls `$this->isPriceViewModeNetto()` (the model *is* the basket), `Service/Factory/PayPalPurchaseUnitsFactory::mapItems()` calls `$basket->isPriceViewModeNetto()`, and `Component/Widget/ArticleDetails::showPayPalExpressOnDetailsPage()` derives the product-price net/gross decision from the session basket's `isPriceViewModeNetto()` (falling back to the shop config only when no basket exists). The shop-global default behaviour (no B2B module, no user override) is unchanged, because `isPriceViewModeNetto()` returns exactly `blShowNetPrice` in that case. Files touched: `src/Model/Basket.php`, `src/Service/Factory/PayPalPurchaseUnitsFactory.php`, `src/Component/Widget/ArticleDetails.php`.
- [0007971](https://bugs.oxid-esales.com/view.php?id=7971): Extend the same B2B net/gross view-mode awareness to `Service/VatOptionsService`. `isNetPriceMode()` now accepts an optional `Basket` and resolves the mode through the user-aware `Basket::isPriceViewModeNetto()` — the passed basket is the primary path, the session basket the fallback, and the raw `blShowNetPrice` shop setting is used only when no basket is available at all. Consequently `getVatOptions()` now reports the *effective* view mode under its `shop.blShowNetPrice` key instead of the raw config value, so the summaries built on top of it (`Service/BasketSummaryService`, `Service/BasketNetSummaryService`) reflect a per-customer / customer-group B2B override. The remaining shop flags (`blShowVATForPayCharge`, `blShowVATForDelivery`, `dDefaultVAT`) stay config-based, as they have no per-user counterpart in OXID. No call-site changes were needed: existing `getVatOptions(null)` callers automatically benefit from the new session-basket fallback. Files touched: `src/Service/VatOptionsService.php`.
- [0007971](https://bugs.oxid-esales.com/view.php?id=7971): Fix the PayPal express-button visibility check in `Core/ViewConfig::isBasketTotalSumGreaterZero()` never evaluating its net-mode branch: the code read `$basket->isPriceViewModeNetto` as a property access (no parentheses) instead of calling the method `$basket->isPriceViewModeNetto()`. PHP resolves the absent property to `null`, so the first operand `($basket->isPriceViewModeNetto && $basket->getNettoSum() > 0)` was always false and the result depended solely on `$basket->getBruttoSum() > 0`. In a pure net-mode / B2B basket where the gross sum can legitimately be zero or unset, the helper wrongly returned false and the express button could be suppressed even though the basket had a value. Fix: call the method. Files touched: `src/Core/ViewConfig.php`.
- Fix abandoned PayPal Express checkouts being logged as two `ERROR` lines with a full stack trace each, even though the situation is entirely normal. When a buyer approves the payment at PayPal but never returns to the shop to complete the order, no shop order is ever created; the `CHECKOUT.ORDER.APPROVED` webhook then arrives for a PayPal order id that has no matching shop order, so `WebhookHandlerBase::getOrderByPayPalOrderId()` raises a `WebhookEventRetryException` ("Shop Order for PayPal order '...' not found"). Previously `RequestHandler::process()` caught `WebhookEventRetryException` together with `ApiException`, logged it at `error` with the exception stack trace ("Webhook transient failure (retry expected)") and rethrew it; the rethrow bubbled up to `WebhookController::init()`, which logged a second `error` ("Webhook processing failed (responding 200 to avoid PayPal retry storm)") and — as it always does — responded HTTP 200. Because the controller returns 200 regardless of the exception, the rethrow produced no different outcome and only generated the duplicate error entry for a perfectly ordinary event. Fix: `RequestHandler::process()` now catches `WebhookEventRetryException` separately and logs it once at `info` level without the stack trace (a missing shop order for a PayPal order id is an expected, benign outcome of an abandoned express checkout, not a failure), and no longer rethrows it — so the second `error` line from the controller is gone as well. `ApiException` keeps its previous `error`-level logging and rethrow, as that represents a genuine transient/infrastructure failure. Files touched: `src/Core/Webhook/RequestHandler.php`.
- [0007964](https://bugs.oxid-esales.com/view.php?id=7964): Fix an uncaught `TypeError` (`Argument #1 ($payPalOrderId) must be of type string, null given`) raised from `Model/Order::finalizeOrderAfterExternalPayment()` when the ACDC finalize step ran with a lost or expired session. `OrderController::finalizeacdc()` reads the PayPal checkout order id via `PayPalSession::getCheckoutOrderId()`, which returns `null` once the session is gone, and passed it straight into the string-typed `finalizeOrderAfterExternalPayment($payPalOrderId, ...)`. Because the resulting `TypeError` is an `Error` and not an `Exception`, the surrounding `catch (Exception ...)` never caught it and the failure surfaced raw in the global exception handler instead of the intended graceful redirect. Fix: `finalizeacdc()` now guards against an empty checkout order id up front and throws `PayPalException::sessionPaymentFail()`, which the existing catch block handles — logging the failure, cancelling the PayPal session and redirecting the customer to `payment?payerror=2`. Files touched: `src/Controller/OrderController.php`.
- [0007963](https://bugs.oxid-esales.com/view.php?id=7963): Fix the standard PayPal smart button briefly opening and then immediately closing the PayPal popup with a visible `Uncaught Error: Expected an order id to be passed` (PayPal JS SDK, observed on v5.0.556) when the customer clicked the button on the order step ("Jetzt kaufen") without confirming the terms-and-conditions checkbox. Root cause: the terms check (`checkTermsAndConditions()` in `paypal-frontend-payment-controller-base.js`) was evaluated *inside* `createOrder` and, on failure, did a bare `return;` — so `createOrder` resolved to `undefined`. The PayPal SDK opens the popup synchronously on click and only then calls `createOrder`; a missing order id therefore tripped the SDK's strict order-id check and surfaced as the console error plus a popup that closed at once (previously, before the SDK's strict check, the same `undefined` return left the button spinner hanging silently). Fix: the check is now performed up front in an `onClick(data, actions)` handler added to the button settings in `paypal-frontend-standard-payment-controller.js`, which shows the localized `READ_AND_CONFIRM_TERMS` message and calls `actions.reject()` before the popup opens — matching the existing Apple Pay (`applepay.tpl`) and Google Pay (`paypal-frontend-googlepay-payment-controller.js`) behaviour. The `createOrder` guard is kept as a safety net. Files touched: `resources/build/js/paypal-frontend-standard-payment-controller.js` (source file and the concatenated `paypal-frontend.min.js` were updated).
- [0007962](https://bugs.oxid-esales.com/view.php?id=7962): Fix orders placed through the PayPal checkout being stored with a foreign payment method (e.g. `OXPAYMENTTYPE = oxidamazon`) instead of the PayPal one, when the basket still carried a payment method from an earlier, abandoned express checkout (typically Amazon Pay). `OrderManager::createShopOrder($paymentId)` applied the PayPal payment id only when the basket had no payment method assigned (`if (empty($this->basket->getPaymentId()) && !empty($paymentId))`, introduced with the PP-Express order-management rework), so a stale `oxidamazon` selection left on the basket was kept. Because the same method sets the `isPayPalPaymentCheckout` session flag, `finalizeOrder` then skips the regular payment execution (`Model/Order::_executePayment` early-returns true when the flag is set) and marks the order `OK`; the PayPal capture still runs via the JS flow, so the customer is charged via PayPal while the order record shows the foreign payment method — breaking reconciliation, refunds and ERP/settlement. Fix: the payment id passed by the checkout flow is now authoritative and always applied (`if (!empty($paymentId))`), overriding any leftover basket payment. As a safety net for the case where no payment id is passed, the method now verifies the resulting basket payment is actually a PayPal payment (`PayPalDefinitions::isPayPalPayment`) and aborts with a logged error otherwise — the callers (`AjaxPaymentController::createOrdersForPayPal` / `createShopOrder`) turn the null result into an error response instead of finalizing a mispaid order. The Amazon Pay module is only the trigger — any express provider that leaves a stale basket payment would expose the same latent issue — so the fix is kept self-contained in the PayPal module. Files touched: `src/Service/OrderManager.php`.

## [2.9.1] - YYYY-MM-DD

### FIX

- Fix PayPal order creation failing with HTTP 422 `AMOUNT_MISMATCH` when a payment-method surcharge is configured together with `blShowVATForPayCharge`. The amount validator's `payment_vat` compensation subtracted the surcharge VAT from the items total and oversized the balancing adjustment, so the breakdown exceeded the order total by exactly the surcharge VAT. Removed that faulty compensation (thanks to **@reyneke-vosz**, PR #611) and, as an optimisation, the payment surcharge is now emitted as a proper line item with a correct net/VAT split (net mode) or gross amount (gross mode) — so it is reflected accurately in `item_total`/`tax_total` instead of as a tax-free "Rounding Adjustment". Files: `src/Service/PayPalAmountValidator.php`, `src/Service/Factory/PayPalPurchaseUnitsFactory.php`.
- [0007954](https://bugs.oxid-esales.com/view.php?id=7954): Fix the tracking code sent to PayPal via API not being stored in the legacy `oxorder.oxtrackcode` field. After a successful `sendtracking()` call to the PayPal API, the tracking code is now also written to `oxorder.oxtrackcode` via the new `Model/Order::setPayPalOrderTrackingCode()` method, making it visible in the standard OXID order admin and accessible to ERP/Wawi systems that read `oxtrackcode` directly.
- [0007951](https://bugs.oxid-esales.com/view.php?id=7951): Fix "session takeover" between PayPal checkout attempts where a stale PayPal order id from an earlier (cancelled or abandoned) checkout was reused in a subsequent attempt, producing two symptoms: (1) the OXID order's `oxorderdate` was minutes-to-hours later than the PayPal capture's `create_time` because the second attempt inherited the first attempt's PayPal order, so the merchant's PayPal admin showed "paid two hours before the order was placed"; (2) when the customer switched payment method between attempts (e.g. ACDC abandoned → PUI retried in the same browser session), the new PayPal order carried the previous attempt's `custom_id` (the stornoed OXID order number), causing webhook deliveries to resolve to a confusing shop-order context for support reconciliation. Root cause: `Model/Order.php::cancelPayPalOrder` removed only `SESSION_CHECKOUT_ORDER_ID` from the PayPal session via `PayPalSession::unsetPayPalOrderId()` after a successful storno, leaving the heavier session state in place (`SESSION_CHECKOUT_ORDER` array snapshot, `paymentid` session variable, `basket->setPayment()` selection, basket-bound `oxorder` id). Three of the four callers of `cancelPayPalOrder` (the UAPM and Express failure branches in `_executePayment`, and the regular cancel path in `Service/Payment::removeTemporaryOrder`) did not compensate for this minimal cleanup — only the `removeTemporaryOrder` cancel-blocked branch (PayPal-side already approved/captured) invoked the broader `PayPalSession::unsetPayPalSession(false)`. The result was an asymmetric session-reset that left the customer's session attached to the cancelled PayPal order; the next checkout attempt's `getCheckoutOrderId()` returned the stale id and no fresh `POST /orders` was issued, so the new OXID order was glued to the old PayPal order. Fix: in `cancelPayPalOrder`, after the two safety guards (`isOrderSuccessfullyPaid` / `isPayPalOrderApprovedOrCaptured`) have early-returned (so this code path runs only on an actual storno), replace the single `PayPalSession::unsetPayPalOrderId()` call with `PayPalSession::unsetPayPalSession(false)` and additionally clear `basket->setOrderId(null)`. The `false` argument preserves `sShipSet` and `$basket->setShipping()` so the customer keeps their delivery address and shipping method on retry — only the PayPal-specific state (`SESSION_CHECKOUT_ORDER_ID`, `SESSION_CHECKOUT_ORDER`, `paymentid`, `basket->setPayment()`) and the basket→order link are dropped. This matches what `removeTemporaryOrder` already does in its cancel-blocked branch; centralising the cleanup in `cancelPayPalOrder` means all four call sites now get a consistent reset. Customer-visible effect on retry: the customer lands on `cl=payment` (the natural redirect target after `ORDER_STATE_PAYMENTERROR`), re-picks a payment method (intended — switching from a failing ACDC attempt to PUI is the common case), keeps basket contents, addresses and shipping, and the next `POST /orders` creates a fresh PayPal order properly attached to the new OXID order. The `removeTemporaryOrder` cancel-blocked branch still does its own `unsetPayPalSession(false)` + `setOrderId(null)` redundantly — kept as defence-in-depth since that path also runs from contexts (ProxyController capture failure) where the underlying `cancelPayPalOrder` may early-return without reaching the new cleanup. Files touched: `src/Model/Order.php`.
- [0007951](https://bugs.oxid-esales.com/view.php?id=7951): Fix `DatabaseErrorException(code: 1062): Duplicate entry '<orderid>-<paypalorderid>-<txnid>' for key 'ORDERID_PAYPALORDERID_TRANSACTIONID'` when multiple PayPal webhooks (`CHECKOUT.ORDER.APPROVED`, `CHECKOUT.ORDER.COMPLETED`, `PAYMENT.CAPTURE.COMPLETED`) for the same capture arrive at the shop in the same second and race on the `oscpaypal_order` UNIQUE index. Observed in production after the "Order too fresh" backoff window (`WebhookHandlerBase::handleWebhookDelay` returns HTTP 503/Retry-After for ~30s after order placement to give the foreground `finalizeOrder` time to commit) expires: PayPal's three queued retries all hit the webhook endpoint within the same second, three parallel workers each enter `OrderRepository::paypalOrderByOrderIdAndPayPalId`, each sees no existing row for the `(oxorderid, oxpaypalorderid, oscpaypaltransactionid)` tuple, each builds a fresh `PayPalOrder` model with a freshly assigned `oxid`, and each calls `$paypalOrderModel->save()` from `WebhookHandlerBase::updateStatus`. One INSERT wins, the other two raise the duplicate-key exception and return HTTP 500 — PayPal then retries those indefinitely, flooding the error log with stack traces even though the order has already been correctly tracked. Root cause: the `load()` / `assign()` / `save()` sequence is a non-atomic check-then-insert. Between the initial `load()` returning unloaded and the eventual `save()` from the caller, concurrent webhook deliveries can each pass the empty-row check. Fix: in `OrderRepository::paypalOrderByOrderIdAndPayPalId`, when the initial `load()` returns an unloaded model, claim the `(oxorderid, oxpaypalorderid, oscpaypaltransactionid)` tuple atomically via `INSERT IGNORE INTO oscpaypal_order` (new private helper `insertIgnorePayPalOrder`). MySQL's `INSERT IGNORE` is atomic with respect to the UNIQUE index: only one of the concurrent statements actually inserts the row, the others silently no-op. After the statement the row is guaranteed to exist; the method then re-runs `getId()` + `load()` on it and returns a loaded model. The caller's subsequent `setTransactionType()`/`setStatus()`/`save()` chain therefore issues an UPDATE rather than an INSERT — no more collisions on the UNIQUE index. The `INSERT IGNORE` writes only the five guaranteed-known columns (`oxid`, `oxshopid`, `oxorderid`, `oxpaypalorderid`, `oscpaypaltransactionid`, `oscpaypaltransactiontype='capture'`); status, PUI payment reference, deposit bank details and other webhook-derived fields are populated by the caller's UPDATE as before. The existing empty-shopOrderId safeguard (refuse to write tracking rows without a shop order id, introduced in 2.8.2 for 0007916) is preserved and still fires before the INSERT, so orphaned rows cannot be created by this change. Behavioural note on status ordering: with the load+UPDATE semantics, the final `oscpaypalstatus` value reflects whichever webhook completed its UPDATE last in the concurrent batch — for typical PayPal delivery (APPROVED first, COMPLETED last) this still yields the expected COMPLETED state, identical to the pre-fix outcome after PayPal's retry storm had eventually resolved. The duplicate-key exceptions and HTTP 500 responses are now gone, and PayPal no longer needs to retry over hours/days for events that were in fact processed. Files touched: `src/Service/OrderRepository.php`.
- Follow-up to 0007944 (2.8.4): vouchers were still missing from the order-confirmation mail for ACDC, Apple Pay, Google Pay and the vaulted-payment `completeOrder` flow. The 0007944 fix added the `$skipProxyControllerVoucherGuard` property and used it to bypass the proxy-controller skip in `Model/Order::_markVouchers`, but only at the foreground `finalizeOrderAfterExternalPayment` call site — the **event-driven** mail send via `EventSubscriber/PayPalOrderCompletedSubscriber::onOrderCompleted` (fired from `AjaxPaymentController::captureOrder` after a successful ACDC/ApplePay/GooglePay capture) and the **vaulted-payment** mail send via `AjaxPaymentController::sendPayPalOrderMail` (called from `completeOrder`) both still hit `sendPayPalOrderByEmail` directly. At those call sites the path is: `_sendOrderByEmail` → `_markVouchers` → guard fires (`isProxyControllerPayment($sessionPaymentId) == true && skipProxyControllerVoucherGuard == false`) → returns null → `Order::$_aVoucherList` stays empty → parent `_sendOrderByEmail` renders the confirmation mail without the voucher line. The merchant's PayPal admin order block and `oxvouchers.oxorderid` were still populated (because `finalizeOrderAfterExternalPayment` ran later in the `cl=order&fnc=finalizeacdc` redirect and bound the voucher — its own `sendPayPalOrderByEmail` was then suppressed by the `isPayPalPaymentCheckout` duplicate-send guard), but the customer's mail had already gone out without the voucher line. Refactor: extracted the existing `try/finally` + `_markVouchers` + `sendPayPalOrderByEmail` choreography out of `finalizeOrderAfterExternalPayment` into a new public method `Model/Order.php::sendPayPalOrderByEmailWithVoucherBinding(User $user, Basket $basket)` that flips `$skipProxyControllerVoucherGuard = true`, calls `$this->_markVouchers($basket, $user)` inside try/finally, and then calls `sendPayPalOrderByEmail()` once the flag is reset. Replaced the four mail-send call sites that need voucher binding (`finalizeOrderAfterExternalPayment` main path, the same method's "healing mail" early-return branch from 0007941, `PayPalOrderCompletedSubscriber::onOrderCompleted`, and `AjaxPaymentController::sendPayPalOrderMail`) with calls to the new helper. `Model/Order::sendPayPalOrderByEmail` itself stays unchanged and remains the underlying mail-send entry point — used unchanged by the failure branch of `finalizeOrderAfterExternalPayment` (where voucher binding is intentionally skipped because no payment was confirmed). The `$skipProxyControllerVoucherGuard` property stays `private` (no public setter) so external callers cannot accidentally flip it; the controlled access is exclusively through the new method. Idempotency note: when both the subscriber and the redirect-path `finalizeOrderAfterExternalPayment` run for the same order (the normal ACDC flow), the second `_markVouchers` call sees the voucher already bound to this order — OXID core's `Voucher::markAsReserved` / `markAsUsed` treat a same-order rebind as a no-op, so no duplicate row or error. Considered alternative was an external public setter for the guard flag (as proposed in PR #610) — rejected to keep the encapsulation: the flag is an internal implementation detail of the proxy-controller skip mechanism, not a behaviour switch foreign modules should be able to toggle. Files touched: `src/Model/Order.php`, `src/EventSubscriber/PayPalOrderCompletedSubscriber.php`, `src/Controller/AjaxPaymentController.php`.

## [2.8.4] - 2026-05-15

### FIX

- [0007929](https://bugs.oxid-esales.com/view.php?id=7929): Fix PayPal refund rejected with HTTP 400 `INVALID_PARAMETER_SYNTAX` on `/amount/value` when the refund amount crosses the thousand. Observed in production with a refund of 5326.00 EUR; PayPal's response: `{"issue":"INVALID_PARAMETER_SYNTAX","field":"/amount/value","value":"5,326.00","description":"The value of the field does not conform to the expected format."}` — the value was sent with a comma thousands separator (`"5,326.00"`), but PayPal's v2 payments API requires the plain dotted-decimal form (`"5326.00"`). Root cause: `Controller/Admin/PayPalOrderController.php::refund()` built the value via `number_format($refundAmount, $currency->decimal, '.', null)`. Since PHP 8.1 `null` is no longer silently coerced to `""` for the fourth `number_format` argument (`thousands_separator`); instead the function falls back to the default value of the parameter, which is `","` — so any refund amount ≥ 1000 produced a comma-separated string. (PHP < 8.0 happened to coerce `null` to `""` and never showed the bug; the regression surfaced for merchants who upgraded their PHP runtime.) Fix: replace the fourth argument `null` with the explicit empty string `''`. All other `number_format()` call sites in the module that feed PayPal-API payloads (`Service/Factory/PayPalPurchaseUnitsFactory.php`, `Service/PayPalAmountValidator.php`, `Core/PayPalRequestAmountFactory.php`, `Controller/ProxyController.php`) already use `''` — only the refund call site had the regression.
